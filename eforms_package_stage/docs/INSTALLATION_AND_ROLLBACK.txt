INSTALLATION — maximum four steps; user-managed only
1. Backup database and application files. Confirm a restore path and pause form-authoring during maintenance. This unsigned RC is not for https://pkdkb.epejabat.net/upgrade. Test on isolated staging first; browser acceptance is still pending.
2. Extract the deployment ZIP to /home/epejabat/pkdkb.epejabat.net/. It creates only eforms_package_stage/ (protected) and eforms-package-preflight.php; payload is NOT installed by extraction. Verify the staging URL denies public access. Log in as Super Admin, open https://pkdkb.epejabat.net/eforms-package-preflight.php and enter the existing 12-digit Installation Key. Proceed only if every check is PASS. Do not bypass mismatch, untracked table, signature or existing deployment policy.
3. If controlled manual installation is allowed and preflight PASS, use cPanel to copy the CONTENTS of eforms_package_stage/payload/ to the root, preserving relative app/assets/database paths. Only manifest files may be replaced; back up those exact files first. Open https://pkdkb.epejabat.net/eforms?visual_migration=1 and use the existing key-protected module migration/automatic-backup action. Apply pending 210/211/212 only; 200/201 must already be applied with matching checksums. Stop on backup or migration failure.
4. Open https://pkdkb.epejabat.net/eforms?packages=1. Upload an example FORM_PACKAGE ZIP, review, choose authorised local reviewers and confirm DRAFT. Preview desktop/mobile, confirm PDF maps, then explicitly publish when authorised. Staff library: https://pkdkb.epejabat.net/eforms?library=1. Execute the controlled smoke checklist before acceptance. Remove the preflight PHP and staging folder after successful verification and retain backups offline/private.

ROLLBACK
Before migration: restore only replaced files from the recorded baseline; remove only newly added files listed in manifest. Preserve configuration, uploads, Staff IDs and unrelated modules.
After additive migrations: do not automatically DROP new tables or delete the migration ledger. Keep maintenance mode; restore the affected old files only after reviewing compatibility. New imported forms/submissions may depend on the new renderer; prevent access pending recovery. A full database restore requires a verified backup and explicit approval because it can lose later writes. Restore to an isolated database first, check counts/foreign keys/ledger and application login. Database automatic rollback is NOT claimed or tested here.
Partial DDL failure: stop, preserve failure logs/started ledger and backups. Do not rerun SQL blindly. Reconcile schema with the backup and obtain recovery approval.
Revision rollback: use Studio Restore as a NEW DRAFT, review workflow/mapping and republish; existing submitted versions remain unchanged.
