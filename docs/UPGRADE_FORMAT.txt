SIGNED VERSIONED UPGRADE FORMAT

/upgrade is Super Admin only, requires CSRF and current password. Upload one signed ZIP plus its independently published SHA256. Payload is staged in protected storage/upgrades, not extracted over the live root. Run Automated Preflight, confirm the actual database backup and explicitly authorize installation. Successful preflight grants one session-bound installation authorization for 10 minutes; the install consumes it and repeats preflight under deployment locks.

ZIP: manifest.json, manifest.sig (base64 RSA/SHA256 signature over exact manifest bytes), payload/root/<relative application path>. No other entries, directory entries or symlinks allowed. Limits: 32MiB compressed, 64MiB expanded, 8MiB per file, 300 entries; strict ratio/path/duplicate checks. No uploaded PHP is executed during verification/staging.

Manifest fields: format=epejabat-upgrade-v1; publisher=epejabat-v1; module=training or core; version=MAJOR.MINOR.PATCH; php_min=8.2; files=[{file:root/...,before_sha256:<existing hash or null for absent>,after_sha256:<payload hash>}]; shared_core_changes=[every explicitly allowlisted Core path]; migration_adapter=none/training-v1/core-v1; migrations=[{file,version}]. Training versions are training:T1:<basename> or training:FULL:<basename>; Core versions are migration basenames. Include existing migration files when declaring a Training adapter so the entire immutable ledger is verified. Apply only pending files; changed applied checksums and untracked table conflicts fail closed. Destructive SQL is refused by default.

Trust is anchored in protected config/upgrade-trust.php. This release contains only a public publisher key; no signing private key or production credentials. A ZIP hash alone does not establish publisher trust. Authentication/configuration/upgrader security files are excluded from ordinary package replacement. Core changes require a dedicated reviewed allowlist and typing APPROVE SHARED CORE CHANGES in addition to password confirmation. New Core paths and new future module namespaces need an explicitly reviewed trust policy release; arbitrary uploaded modules cannot grant themselves trust. Do not use unsigned archives or manually edit expected hashes to bypass a conflict.

Versions are stored in system_settings and upgrade_history. The immutable migration ledger and signed run reports record actual file/migration results. Local installation verification never means production browser smoke tests have passed. All future approved updates use /upgrade. Files/database recovery is documented separately; automatic database rollback is not promised.
